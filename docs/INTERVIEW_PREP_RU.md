# VOEEMSOG — подготовка к собеседованию (MixRank)

Этот документ основан на коде ZIP-архива Java-backend. **Не заучивай вымышленные истории**: примерные ответы о выборе технологий — интерпретация архитектуры; реальную причину выбора и реальные инциденты можешь подтвердить только ты. В каждой истории разделяй *что было*, *что сделал*, *чем измерил результат*.

## 1. Твой 60-секундный рассказ о проекте

**Русский черновик:** «Я самостоятельно разработал первоначальный backend контентного сайта VOEEMSOG на Java 21 и Spring Boot. Он предоставлял REST API для комнат с переводами, публикаций, историй, музыки и пожертвований; данные хранились в PostgreSQL через Spring Data JPA. Для админских операций я написал собственный фильтр проверки токенов в HttpOnly cookie. Позже мы перенесли backend на Supabase из-за стоимости инфраструктуры. Java-код сохранил в публичном репозитории. При подготовке портфолио отдельно разобрал, какие решения были удачными, а какие теперь сделал бы иначе». **Используй только если каждое утверждение соответствует твоему участию.**

**English:** “I independently built the original backend of the VOEEMSOG content website with Java 21, Spring Boot and PostgreSQL. It exposed REST APIs for multilingual rooms, posts, stories, music and donations. I implemented the data-access layer with Spring Data JPA and a custom cookie-token filter for the admin endpoints. We later migrated the product to Supabase to reduce hosting costs. I preserved the original Java code and reviewed its trade-offs and security limitations.”

## 2. Почему Java + Spring Boot, а не Python / FastAPI / Node.js?

**Основа ответа:** на момент разработки ты мог продуктивнее всего создавать типизированный backend на Java; Spring Boot давал HTTP, dependency injection, persistence и security в одной экосистеме. **Не говори, что Java объективно быстрее Python для любого API.** В MixRank стоит показать готовность учить Python/Rust: «Я выбираю инструмент под масштаб, задачи и команду; изучаю Python и SQL там, где это оправдано» — лишь если это правда.

**Возможное уточнение:** Java многословнее и требует больше ресурсов, но удобна для долгоживущего backend с явно типизированными моделями. Python может быть лучше для обработки данных, автоматизации и интеграции с аналитическими инструментами.

## 3. Почему PostgreSQL, а не MongoDB / H2?

**По коду:** модели имеют отношения (`Room` → `RoomTranslation`, `Album` → `Track`), JPA-репозитории используют JOIN, сортировки и фильтры. SQL-реляционная модель подходит для связанной структуры. H2 присутствовала как зависимость, но локальный `data/` был артефактом окружения, не доказательством production-использования. MongoDB можно выбрать для более гибких документов, но здесь важны связи и запросы.

**Вопрос:** «Какие индексы нужны?» — начни с реальных запросов: `rooms.code`, `room_translations (room_id,lang)`, `rooms.date`, поля фильтров, учитывая план запросов (`EXPLAIN ANALYZE`). Не утверждай, что все индексы уже есть.

## 4. Почему Spring Data JPA? Что такое N+1?

JPA сокращает ручной CRUD-код и преобразование строк в объекты. Неприятная сторона — неявные запросы и ленивые отношения. В `RoomService.fillWithDto()` для каждой комнаты вызывается запрос перевода по `room+lang`: для списка из N комнат это потенциально 1+N запросов. Это **выявленная проблема**, а не подтверждённый прежний production-инцидент. Исправление — одним запросом `JOIN`/projection получить нужные переводы, сравнить число запросов и время ответа до/после.

## 5. Почему отдельная таблица RoomTranslation?

`Room` хранит общие поля (code, dangerType, size, date), `RoomTranslation` — `lang`, `name`, `description`. Это позволяет не дублировать комнату ради каждого языка и добавлять переводы отдельно. Минусы: JOIN-ы, ограничения уникальности `(room_id, lang)` и контроль согласованности переводов. Проверь язык запроса: в коде используется `lang` как обязательный параметр.

## 6. Как устроена админская авторизация?

`POST /admin/login` сравнивает ключ с `SECOND_API_KEY`, генерирует UUID, сохраняет время выдачи в памяти процесса, ставит `admin_token` как HttpOnly + Secure + SameSite=None cookie. `AdminTokenFilter` читает cookie, проверяет срок 30 минут и кладёт роль `ROLE_ADMIN` в SecurityContext. Большинство `/admin/**` защищено `authenticated()`.

**Почему не JWT?** Серверные opaque tokens проще отозвать и не требуют проверки JWT-подписи, но хранят состояние и не масштабируются горизонтально без общего хранилища. **Что бы улучшил:** Redis + TTL или Spring Security session management, ограничение логинов, точная политика CORS, CSRF защита, единый logout/cookie policy, аудит, HTTPS. `SameSite=None` и отключённый CSRF особенно важно уметь объяснить.

## 7. Какие баги и сложности ты решал?

**ВНИМАНИЕ: ниже — реальные проблемы/риски, обнаруженные статическим ревью, но НЕ свидетельства того, что они происходили во время разработки.** Для интервью используй их как «при повторном ревью я обнаружил и исправил ...», если изменения действительно применены и проверены.

**Кейс A — `NullPointerException` при отсутствующем секрете.** В исходном `AdminLoginController` было `System.getenv("SECOND_API_KEY").equals(apiKey)`, а в webhook — аналогичный вызов для `KOFI_KEY`. Если переменная отсутствует, код падает. В портфолио-копии сравнение переписано на null-safe. **Расскажи:** анализ ветвления → проблема → корректная обработка неустановленного ключа. **Ещё улучшить:** конфигурация с обязательной проверкой при запуске.

**Кейс B — многопоточные обращения к токенам.** Изначально токены хранились в обычном `HashMap` singleton-сервиса. Параллельные HTTP-запросы потенциально небезопасны. Заменено на `ConcurrentHashMap`, но для production нужен общий store и TTL-очистка. **Не утверждай**, что это был воспроизведённый race condition.

**Кейс C — `roomToDTO(null, ...)`.** Сервис получал `Optional.orElse(null)` и разыменовывал `room`. Добавлена проверка на null, чтобы отсутствующая комната не вызывала NPE. HTTP-ответ сейчас неидеален (в некоторых случаях 204 вместо 404), это отдельная задача.

**Кейс D — webhook.** `DonationController` принимает Ko-fi form field `data`, разбирает JSON, проверяет `verification_token` и увеличивает сумму цели. Однако catch-all возвращает 200 даже при ошибках, без retry/алерта, и нет идемпотентности. Поэтому **не выдумывай**, что у тебя уже есть exactly-once обработка. Предлагаемое решение: уникальный ID события + уникальный индекс + транзакция + чёткие ответы при сбоях + мониторинг.

**Кейс E — точность денежных сумм.** `float` у `Donation.amount` и целей приводит к ошибкам двоичного представления. Правильнее `BigDecimal` и SQL `NUMERIC`, но миграция схемы/DTO должна быть согласованной. В этой чистке поведение не менялось.

**Кейс F — пагинация и перевод.** `getRoomsByPage(page, 10, lang)` строит `PageRequest.of(page - 1, limit)`, поэтому при `page=0` выбросит исключение. Надо валидировать `page>=1`; сортировка перевода — отдельный SQL-запрос; при большом списке возможен N+1.

### Шаблон настоящей истории о баге (STAR)

- **Situation:** какая была функция и что реально сломалось? Укажи входной запрос, сценарий и наблюдаемую ошибку.
- **Task:** каковы были требования и что было на тебе?
- **Action:** где логировал, как воспроизвёл, как сузил проблему, какой код/SQL изменил и какие альтернативы отверг?
- **Result:** что изменилось после фикса? Тест, скорость, статус-код, отсутствие повторов — приводи только измеренное.

Заполни для себя хотя бы **две реальные истории**: [ошибка 1 — симптомы, причина, исправление, проверка] и [ошибка 2 — симптомы, причина, исправление, проверка]. Их нельзя достоверно восстановить по одному ZIP без issue tracker / истории коммитов.

## 8. Что ты изменил бы сейчас?

1. Тесты: unit для service, MockMvc для auth/routes, интеграционные с PostgreSQL Testcontainers.
2. Flyway или Liquibase + проверяемая schema migration (в архиве есть только неполная legacy-схема).
3. Обязательная валидация входных DTO, единые HTTP-ошибки, не отдавать Entity напрямую.
4. Транзакции и идемпотентность для пожертвований; `BigDecimal` для денег.
5. Меньше запросов для списка комнат; измерение `EXPLAIN ANALYZE` и индексирование.
6. Безопасность админки: CSRF, общий session store, rate limiting, logging без секретов.
7. Автоматические CI сборка + интеграционные тесты и безопасная конфигурация.

Не говори, что всё это уже внедрил — это roadmap.

## 9. Почему миграция на Supabase?

**Собственная версия, которую стоит подтвердить:** «Для текущего масштаба продукта инфраструктура отдельного Java-сервиса обходилась дороже, чем подходящий бесплатный тариф Supabase. Мы выбрали более дешёвый способ обеспечить нужную функциональность, несмотря на то что исходный Java-backend уже был написан». Не утверждай, что Supabase — drop-in замена Spring или что весь PostgreSQL перенесён без изменений, если это не так.

**Trade-off:** меньше ops и расходов, но больше зависимость от провайдера и ограничения тарифа. Это показывает продуктовое мышление, не техническую неудачу.

## 10. Вопросы от MixRank: подготовь ответ заранее

- **What did you personally implement?** Чётко отдели твой backend от чужого frontend и Supabase-миграции.
- **Which SQL query was hardest?** Покажи JPQL `getRoomsByLang`, `getRoomsByPage`, `RoomTranslation` и объясни JOIN / pagination.
- **How does your app behave with 100k rooms?** Индексы, N+1, keyset pagination, profiling; не заявляй, что тестировал 100k.
- **What happens when two donations arrive simultaneously?** Укажи на race/lost updates в текущей реализации и транзакционное решение.
- **How do you test a webhook?** Валидные/невалидные ключи, повторная доставка, ошибки DB, конкурентные события; предложи MockMvc и integration tests.
- **Why should we hire you for a Python-heavy role?** Подчеркни переносимые навыки: HTTP, SQL, data modeling, Linux/Git, debugging; признай, что Python придется подтянуть, и дай конкретный план обучения.
- **Tell me about a mistake.** Хороший честный пример — токены в `HashMap`, без CSRF, или обработка всех webhook ошибок как 200 — при условии, что ты можешь объяснить последствия и сделанную правку.
